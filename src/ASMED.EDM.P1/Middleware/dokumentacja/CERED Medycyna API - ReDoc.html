Tworzenie e-recepty metodą EAN

Endpoint tworzy jedną lub wiele e-recept na podstawie danych pacjenta, autora oraz listy leków. Pola patient, author oraz medicines są przekazywane jako JSON zakodowany w stringu w multipart/form-data, a nie jako natywne obiekty JSON. Dla czytelności dokumentacji schematy logiczne danych wejściowych są opisane osobno jako: - PatientEanInput - AuthorEanInput - MedicineEanInput - MedicinesEanInput Ważne reguły walidacji: - dla leku nierecepturowego wymagane jest packageId albo ean - ds jest wymagane tylko wtedy, gdy receptaRok = false - dla recepty rocznej (receptaRok = true) należy przekazać: dosingValue i dosingRepeat albo tablicę periods

  • uprawnienieDod zachowuje kompatybilność wsteczną i może być: pojedynczym stringiem albo tablicą stringów

Uwaga: obligatoryjność pól w schematach jest specyficzna dla tej metody i nie powinna być automatycznie przenoszona na inne endpointy.

Rozszerzone wyszukiwanie recept pacjenta

Certyfikat lekarza może zostać przekazany bezpośrednio w polu doctor_cert. Jeżeli nie zostanie przesłany, system spróbuje użyć certyfikatu przypisanego do numeru PWZ w konfiguracji mikroserwisu. Jeżeli pole page nie zostanie przekazane, domyślnie zostanie użyta wartość 0. EP zwraca na jednej stronie 20 wyników.

Anulowanie pojedynczej e-recepty

Endpoint służy do anulowania pojedynczej e-recepty na podstawie identyfikatora recepty oraz klucza recepty. Wymagane są dane pacjenta, dane autora, identyfikator biznesowy podmiotu, hasło do certyfikatu lekarza oraz dane recepty przeznaczonej do anulowania. Pola patient oraz author są przekazywane jako JSON zakodowany w stringu w multipart/form-data, a nie jako natywne obiekty JSON. Dla czytelności dokumentacji logiczna struktura danych wejściowych jest opisana osobno jako: - PatientDeleteInput - AuthorDeleteInput Certyfikat lekarza może zostać przekazany bezpośrednio w polu doctor_cert. Jeżeli nie zostanie przesłany, system spróbuje użyć certyfikatu przypisanego do numeru PWZ autora w konfiguracji mikroserwisu. Pole patient.postCode powinno być przekazane bez myślnika, jako 5 cyfr, np. 08110. Pole author.clinicPostCode powinno być przekazane w formacie 6-znakowym, np. 08-110.

Wystawienie elektronicznego zwolnienia lekarskiego (ZLA)

Wystawia (podpisuje certyfikatem lekarza i wysyła do ZUS) zaświadczenie ZLA. Pola program, patient, details, platnik oraz workPlace są przekazywane jako JSON zakodowany w stringu w multipart/form-data, a nie jako natywne obiekty JSON — identycznie jak w module e-recepty.

Płatnik i KRUS. Pole platnik jest w całości opcjonalne — zgodnie ze schematem KEDU ZLA (sekcja V, t_DPZLA) zaświadczenie może w ogóle nie mieć wskazanego płatnika składek. Dotyczy to w szczególności pacjentów ubezpieczonych w KRUS (patient.insuredIn = "2", czyli rolników), którzy zwykle nie mają płatnika z numerem NIP — dla nich pole platnik należy pominąć albo przesłać jako pusty obiekt {}. Jeśli obiekt jest przekazany, dokładnie jedno z pól NIP / Pesel / SeriaNumerPaszportu powinno być wypełnione (kolejność pierwszeństwa w mikroserwisie: NIP > Pesel > SeriaNumerPaszportu).

sendPlatnikInfo. Pole details.sendPlatnikInfo decyduje, czy kopia zaświadczenia przekazywana do płatnika ma zawierać rozpoznanie (false — płatnik NIE widzi szczegółów/rozpoznania; true — widzi). Nie ma to wpływu na oryginał (ten zawsze zawiera pełne dane).

Słowniki kodów: - patient.insuredIn: 1 = ZUS, 2 = KRUS, 3 = inny podmiot w Polsce, 4 = inny podmiot za granicą. - details.wskazanie: 1 = chory powinien leżeć, 2 = chory może chodzić. - details.kodOpieka (tylko dla zwolnienia z powodu opieki): 1 = dziecko, 2 = małżonek/rodzic/teść/dziadek/wnuk/rodzeństwo itp., 3 = inne osoby. Jeśli podane, wymagane jest też details.opiekunDataUr (data urodzenia osoby, nad którą sprawowana jest opieka). - details.codes (A–E): dodatkowe kody okoliczności niezdolności do pracy zgodne ze wzorem ZUS ZLA — każdy z kodów A,B,C,D,E to osobna flaga logiczna; więcej niż jedna może być true. - platnik — rodzaj identyfikatora wynika z tego, które pole jest wypełnione: NIP → typ 1, Pesel → typ 2, SeriaNumerPaszportu → typ 3.

Znane ograniczenie. Walidator wymaga patient.pesel bezwarunkowo — zaświadczenia dla pacjentów bez nadanego PESEL (identyfikowanych numerem paszportu) nie da się obecnie wystawić przez ten endpoint, mimo że format XML to przewiduje.
